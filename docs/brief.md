# Бриф: `opmin` — тулза минимизации опкодов PHP-кода без изменения поведения

## Цель

CLI-тулза, которая:
1. Считает количество опкодов **на каждую функцию/метод/замыкание** в PHP-коде.
2. Прогоняет код через Rector-правила, пересчитывает опкоды, оставляет только изменения, которые уменьшили счёт.
3. Прогоняет код через LLM-стадию (Claude Code skill с паттернами микрооптимизаций), снова пересчитывает.
4. На каждом шаге проверяет, что поведение не изменилось. Любое изменение, ломающее поведение или не уменьшающее опкоды, откатывается.

Итог — код с минимумом опкодов + отчёт «до/после» по каждой функции.

## Как работать с этим брифом (для агента)

- Реализуй **строго по этапам M0 → M8** из раздела «Этапы и критерии приёмки». Не начинай следующий этап, пока критерии текущего не выполнены и тесты не зелёные.
- Перед каждым этапом — короткий план (какие классы, какие тесты) и только потом код. После этапа — коммит и короткая сводка: что сделано, что отложено, какие решения принял сам.
- **Верификатор (Модуль 2) — самая важная часть.** Если приходится выбирать между «быстрее сделать» и «надёжнее проверить» — выбирай надёжность. Лучше отклонить корректное изменение, чем принять ломающее.
- Если что-то в брифе противоречит реальности (формат дампа OPcache не такой, API Rector изменился, правило не существует) — проверь на практике, напиши, что нашёл, и предложи решение, а не подгоняй код под бриф.
- Не придумывай опкодные «оптимизации» из головы — каждую проверяй реальным подсчётом на текущем PHP.
- Все команды CLI, ключи конфига и форматы файлов — как описано здесь. Отклонение — только с обоснованием в сводке этапа.

## Модуль 1. Подсчёт опкодов

### Как получить опкоды

Компилируем каждый файл **в отдельном процессе**, без исполнения:

```bash
php -d opcache.enable_cli=1 \
    -d opcache.file_cache= \
    -d opcache.jit=0 \
    -d opcache.optimization_level=0x7FFEBFFF \
    -d opcache.opt_debug_level=0x20000 \
    -r 'opcache_compile_file($argv[1]);' path/to/File.php 2> dump.txt
```

- `opt_debug_level=0x10000` — опкоды **до** оптимизатора, `0x20000` — **после**. Снимать оба, основная метрика — **после** оптимизатора (это то, что реально исполняется).
- Дамп идёт в stderr. Парсить заголовки блоков: `$_main`, `functionName`, `ClassName::method`, `{closure}` + строки `(lines=N, args=..., vars=..., tmps=...)`.
- `lines=N` — это и есть число опкодов функции. Дополнительно сохранять `vars`, `tmps` и разбивку по типам опкодов (гистограмма), пригодится LLM-стадии.
- Замыкания и анонимные классы маппить на файл:строку через php-parser (в дампе они безымянные).
- Важно: оптимизатор делает разные вещи в зависимости от контекста (namespace, FQN-функции, известные константы), поэтому всегда компилировать **реальный файл в его namespace**, а не вырезанную функцию.

### Команда `opmin count <path>`

- Рекурсивно по директории или по одному файлу.
- Фильтр: `--filter='App\\Service\\*'`, `--exclude=vendor,tests`.
- Вывод: таблица (функция, файл:строка, ops_raw, ops_opt, vars, tmps), `--format=json` для машинного потребления.
- Итог: суммарный счёт по проекту/файлу.

### Команда `opmin diff <before.json> <after.json>`

- Дельта по каждой функции, сортировка по выигрышу, отдельно — функции, где стало хуже.

## Модуль 2. Проверка поведения («не проебать поведение»)

Это главная часть, без неё тулза бесполезна. Три уровня, применяются по порядку, любой провал = откат шага:

1. **Синтаксис и статика:** `php -l` + PHPStan (уровень как в проекте, но не ниже исходного количества ошибок — новых ошибок быть не должно).
2. **Тесты проекта:** через адаптер тест-раннера (PHPUnit / Pest / Testo / команда, см. «Адаптеры тест-раннеров»). Перед стартом — прогнать на исходном коде, если красные, тулза останавливается.
3. **Дифференциальное тестирование (характеризационные тесты):** для каждой изменённой функции:
   - держать копию исходной версии в отдельном namespace/префиксе (через php-parser переименовать класс/функцию в `__opmin_orig\...`);
   - генерировать входы по типам параметров (из сигнатуры, phpdoc и PHPStan): граничные значения (`0`, `-1`, `''`, `'0'`, `null`, пустой массив, большие числа, unicode-строки, `INF/NAN` для float), плюс N случайных;
   - вызывать обе версии, сравнивать: возвращаемое значение (строго, `===` с учётом float/NaN), брошенное исключение (класс + сообщение), вывод (`ob_start`), изменения by-ref аргументов, состояние `$this` после вызова (через сериализацию/рефлексию);
   - функции с внешними эффектами (I/O, БД, время, рандом) — не тестировать дифференциально, помечать как `unverified` и **не менять без подтверждающих тестов проекта**.

Опционально `--mutation-check`: перед оптимизацией прогнать Infection по целевым функциям и в отчёте показать MSI — если тесты слабые, пользователь должен об этом знать.

### 2.1. Сравнение warnings / notices / deprecations

Это обязательная часть сравнения, а не опция. Типичная оптимизация `$a['x']` → `$a['x'] ?? null` или `array_key_exists` → `isset` убирает warning `Undefined array key`. В Laravel (`HandleExceptions`) и Symfony (`ErrorHandler`) warning превращается в исключение — то есть поведение приложения реально меняется, хотя return-значение одинаковое.

Реализация:
- Перед каждым вызовом (и старой, и новой версии) ставить `set_error_handler` с `E_ALL`, который **записывает** ошибку (уровень `E_WARNING`/`E_NOTICE`/`E_DEPRECATED`/`E_USER_*`, текст сообщения, номер строки **относительно начала функции**, не абсолютный) и возвращает `true` (не прерывает исполнение). После вызова — `restore_error_handler()`.
- `error_reporting(E_ALL)` на время дифф-теста, независимо от настроек проекта.
- Сравнивать последовательность ошибок: уровень + текст. Номер строки не сравнивать (код переписан, строки сдвинулись).
- Отдельный прогон с error handler в режиме **«бросать исключение»** (`ErrorException`), как в фреймворках: проверить, что обе версии бросают на одних и тех же входах.
- Политика в конфиге:
  ```yaml
  verification:
    warnings: strict   # strict — любое расхождение = откат
                       # allow_removal — разрешить, если новая версия убрала warning, но не добавила
  ```
  По умолчанию `strict`. `allow_removal` — только для проектов, где точно нет error-to-exception конвертации, и это пользователь включает сам.
- Также сравнивать: `E_DEPRECATED` (новая версия не должна добавлять депрекейшены целевой версии PHP).

### 2.2. Детектор опасных динамических конструкций

Некоторые конструкции делают видимые оптимизатору «упрощения» неверными. Модуль `DynamicScopeDetector` на php-parser обходит тело каждой функции и помечает её флагами. Флаги учитываются **и в Rector-стадии, и в LLM-стадии** (передаются модели в промпт).

| Конструкция | Почему опасно | Действие |
|---|---|---|
| `compact(...)`, `extract(...)` | Переменные используются/создаются по строковым именам. «Неиспользуемая» переменная на деле используется | Запрещены правила удаления/переименования/инлайна переменных в этой функции |
| `$$name`, `${'name'}` | То же самое | То же |
| `get_defined_vars()` | Результат зависит от набора локальных переменных — удаление/добавление временной переменной меняет результат | Запрещено **любое** изменение набора локальных переменных |
| `func_get_args()`, `func_get_arg()`, `func_num_args()` | Зависит от аргументов, включая изменённые в теле; изменение сигнатуры меняет результат | Запрещено менять сигнатуру и переприсваивать параметры |
| `debug_backtrace()`, `debug_print_backtrace()`, `(new \Exception)->getTrace()` | Зависит от структуры вызовов и номеров строк | Запрещён инлайн/вынос вызовов, функция помечается `line_sensitive` |
| `__LINE__`, `__FUNCTION__`, `__METHOD__` | Зависят от расположения кода | Не переносить через границы функций |
| `eval(...)`, `include`/`require` внутри функции | Подключённый код видит локальную область видимости | Функция целиком исключается из оптимизации (`skip`) |
| `static $var` внутри функции | Состояние между вызовами | Дифф-тестер обязан вызывать функцию **последовательно несколько раз** и сравнивать всю цепочку; не менять порядок инициализации |
| `global $x`, `$GLOBALS` | Побочные эффекты на глобальное состояние | Дифф-тестер сравнивает снапшот затронутых глобалов до/после; функция считается side-effecting |
| Вызов по строке/массиву (`$fn()`, `call_user_func`, `[$obj, $m]()`) | Call site неизвестен | Для **вызываемой** стороны: функция может быть вызвана откуда угодно → менять сигнатуру нельзя |
| `__get`/`__set`/`__call`/`ArrayAccess` у объектов в теле | `isset($obj->x)` и `$obj->x !== null` вызывают **разные** магические методы (`__isset` vs `__get`) | Правила замены `isset`↔сравнения запрещены для свойств/элементов объектов, тип которых не доказан PHPStan как не-магический |
| `Reflection*` над самой функцией/классом | Может читать параметры, атрибуты, docblock | Запрещено менять сигнатуру и docblock |

Флаги сохраняются в JSON `count`-отчёта (`"flags": ["compact", "static_var"]`) — пригодится для отладки и для промпта LLM.

### 2.3. FQN глобальных функций и констант — проверка затенения

`strlen($s)` внутри `namespace App\Foo` в рантайме сначала ищет `App\Foo\strlen`, и только если её нет — глобальную. Замена на `\strlen` или `use function strlen` **отключает этот fallback**. Если где-то объявлена `App\Foo\strlen` (частый приём в тестах для мока `time()`, `file_exists()` и т.п. — см. `php-mock`, `symfony/phpunit-bridge` ClockMock/DnsMock), поведение меняется.

Реализация:
- Перед FQN-стадией собрать **индекс всех namespaced-функций и констант** в проекте, включая `tests/` и `vendor/` (через php-parser по всем `.php`, с кешем).
- Отдельно детектировать динамические объявления: `eval` с `function`, `php-mock` / `ClockMock::register(...)` / `DnsMock::register(...)` в тестах — по известным сигнатурам этих библиотек. Если для namespace найдена регистрация мока — **не трогать** вызовы этих функций в этом namespace.
- Делать FQN только для функций, для которых в данном namespace нет и не может быть одноимённой функции.
- То же самое для констант (`PHP_EOL` → `\PHP_EOL`): проверять `define('App\Foo\PHP_EOL', ...)` и `const` в namespace.

### 2.4. Покрытие дифф-тестов (без этого «проверено» — самообман)

Случайные входы часто не доходят до нужных веток (`if ($x === 'magic-string')`). Поэтому дифф-тесты меряют собственное покрытие и добирают входы.

Реализация:
- Прогон дифф-тестов под **pcov** (быстрый, только line coverage) или **Xdebug** в режиме branch coverage (`xdebug.mode=coverage`, `XDEBUG_CC_BRANCH_CHECK`) — если доступен. Branch coverage предпочтительнее; pcov — fallback.
- Метрика — покрытие **исходной** версии функции (именно её поведение мы фиксируем).
- **Движок генерации — `rasuvaeff/property-testing-core`**, а не свой велосипед. Это ядро property-based testing без зависимости от тест-фреймворка (генераторы `Gen::*`, раннер, **шринкинг** — сведение контрпримера к минимальному, воспроизводимость по seed, граничные значения `edgeCases`, автовывод генераторов из типов параметров и Psalm/PHPStan-аннотаций, корпус найденных падений). Из него берём:
  - генераторы по типам (автовывод из сигнатуры и phpdoc) — это фаза 1 ниже;
  - свои генераторы через `ArbitraryInterface` для пула литералов и мутаций по покрытию (фазы 2–3);
  - **шринкинг**: когда версии разошлись, контрпример сжимается до минимального — в отчёт и в сгенерированный тест идёт короткий понятный вход, а не массив на 200 элементов;
  - seed и корпус: упавшие входы сохраняются в `runs/<ts>/corpus/` и при повторном прогоне той же функции проверяются первыми.
  - Свойство, которое проверяем, одно: «для любого входа `old(x)` ≡ `new(x)`» (сравнение по правилам 2.1, 2.4, 2.5).
  Перед использованием — прочитать README и исходники пакета в `vendor/`, выяснить, как вызывать раннер программно (без `#[Property]` и тест-фреймворка), как подключать свои генераторы и как получить шринкнутый контрпример. Записать в `docs/testing.md`.
  Риски: пакет молодой, один автор, мало звёзд. Обернуть его в наш интерфейс `InputGenerator`/`PropertyRunner` (тонкий адаптер), чтобы при проблемах можно было заменить реализацию, не трогая верификатор. Версию зафиксировать точно. Важно: старый пакет `rasuvaeff/property-testing` заброшен — использовать только `-core` и `-testo`.
- Генерация входов в три фазы:
  1. **Граничные значения** по типу (см. выше).
  2. **Константы из тела функции:** php-parser вытаскивает все литералы из функции (строки, числа, ключи массивов, имена в `match`/`switch`/`in_array`), и они добавляются в пул значений для соответствующих параметров, плюс соседние значения (`n-1`, `n`, `n+1`, строка с префиксом/суффиксом). Это дёшево и закрывает большинство веток вида `=== 'magic'`.
  3. **Добор по покрытию:** пока покрытие растёт — мутировать входы, которые открыли новые ветки (простой coverage-guided fuzzing: изменить один аргумент, комбинировать значения из пула). Лимит по времени на функцию (`verification.fuzz_time_ms`, по умолчанию 2000).
- Порог:
  ```yaml
  verification:
    min_branch_coverage: 90   # % веток исходной функции, покрытых дифф-тестами
  ```
  Не достигли — функция `unverified` (если её не покрывают тесты проекта, что тоже проверяется через coverage проектных тестов) и по умолчанию **не меняется**.
- Ветки, недостижимые по коду (мёртвый код), отмечаются по анализу PHPStan и не учитываются в знаменателе.
- В отчёте у каждой функции: покрытие дифф-тестами, покрытие тестами проекта, итоговый статус.
- **Найденный контрпример** (вход, на котором версии расходятся) сохраняется в отчёт и в `runs/<ts>/counterexamples/` как готовый тест **в формате тест-раннера проекта** (PHPUnit / Pest / Testo — генерирует адаптер) — пользователь может забрать его в свой проект.

Как вызывать функции разных видов:
- обычная функция — напрямую;
- статический метод — `Class::method(...)`;
- метод экземпляра — объект создаётся: (а) через конструктор с сгенерированными аргументами, (б) если не получилось — `ReflectionClass::newInstanceWithoutConstructor()` + заполнение свойств сгенерированными значениями по типам. Обе версии получают **глубокие копии одного и того же** объекта (`unserialize(serialize())` или клонирование через рефлексию, если сериализация запрещена);
- `private`/`protected` — через `Closure::bind`;
- замыкания — извлекаются по позиции в файле, вызов через возврат замыкания из обёртки (если захватывают `use`-переменные — значения генерируются).
- Если зависимостей конструктора не создать (интерфейсы, сервисы) — генерировать **моки** интерфейсов, которые возвращают детерминированные значения по типу возврата и **записывают** последовательность вызовов. Сравнивается и результат, и журнал вызовов моков (порядок, аргументы). Это ловит изменение порядка побочных эффектов.

### 2.5. Детерминизм дифф-тестов

Если тест сам по себе флапает, сравнение бессмысленно. Перед сравнением версий каждую функцию гоняем на одном входе **дважды на исходной версии**: если результаты расходятся — функция недетерминированная, отдельная обработка.

Источники недетерминизма и что с ними делать:
- **Время** (`time()`, `microtime()`, `date()`, `new \DateTime()`, `hrtime()`): подменять через namespaced-функции (тот же приём, что php-mock) на фиксированное значение для обеих версий. Если используется Carbon / Symfony Clock — `Carbon::setTestNow()` / `MockClock`.
- **Рандом** (`rand`, `mt_rand`, `random_int`, `random_bytes`, `shuffle`, `array_rand`, `uniqid`, `Random\Randomizer`): `mt_srand(seed)` перед каждым вызовом; для `random_int`/`random_bytes` — подмена namespaced-функциями на детерминированный генератор. Если подменить нельзя — функция `nondeterministic` → `unverified`.
- **Идентичность объектов** (`spl_object_id`, `spl_object_hash`, `===` между объектами): при сравнении результатов объекты сравнивать **структурно** (рекурсивно по свойствам через рефлексию), а не по идентичности; id нормализовать (заменять на порядковый номер первого появления).
- **Float:** сравнивать с относительным допуском `1e-12`, но `NAN` равен только `NAN`, `-0.0` и `0.0` **различаются** (`1/-0.0` даёт `-INF`), `INF` по знаку. Допуск конфигурируется; `0` — побитовое сравнение.
- **Порядок ключей массивов:** сравнивать **с учётом порядка** (`===` для массивов в PHP учитывает порядок — так и надо; переупорядочивание ключей — это изменение поведения, потому что ломает `foreach` и `json_encode`).
- **Ресурсы** (файлы, сокеты): функции, принимающие/возвращающие resource, — `side_effecting`, только тесты проекта.
- **Окружение** (`getenv`, `$_SERVER`, `php_uname`, `memory_get_usage`, `gc_*`): фиксировать снапшот окружения перед каждым вызовом, `memory_get_usage` и подобные — функция `nondeterministic`.
- Каждый вызов функции — в **изолированном состоянии**: сбрасывать статические свойства затронутых классов (снапшот через рефлексию до вызова, восстановление после) и `static`-переменные функций (для этого прогоны группировать по свежему процессу, если иначе нельзя).
- Дифф-тестер запускается в отдельном процессе (`proc_open`) с `memory_limit` и `max_execution_time`; бесконечный цикл или OOM на входе — сравниваем факт таймаута/OOM у обеих версий (если исходная тоже зависает на этом входе — вход выкидываем).

## Модуль 3. Пайплайн оптимизации

### Команда `opmin optimize <path>`

Работает в git-рабочем дереве (требовать чистый `git status`) или в копии каталога. Каждый принятый шаг — отдельный коммит, чтобы было видно, что и почему поменялось.

```
baseline:   count → сохранить runs/<ts>/00-baseline.json
stage A:    Rector (по одному правилу)
stage B:    LLM-стадия (skill), по одной функции
final:      count → отчёт
```

### Stage A — Rector

Stage A состоит из двух групп правил:

| Группа | По умолчанию | Что это |
|---|---|---|
| **Свои правила opmin** (`rector.custom_rules`) | **Включены** | Правила, написанные специально под минимизацию опкодов, со встроенными проверками безопасности (см. «Свои Rector-правила»). Каждое можно отключить по отдельности |
| **Стандартные правила Rector** (`rector.standard`) | **Выключены** | Правила и наборы из поставки Rector. Список всегда лежит в конфиге, вся группа включается одной строкой `enabled: true` или флагом `--with-standard-rector` |

Почему стандартные выключены по умолчанию:
- они писались не под опкоды, а под апгрейд версий и качество кода — большая часть ничего не даст по опкодам и только зашумит дифф и замедлит прогон;
- они не знают про наши условия безопасности (`DynamicScopeDetector`, затенение функций, warnings) — их изменения ловит только верификатор, а не само правило;
- в проектах, где уже настроен свой Rector, пользователь может не хотеть, чтобы чужой набор правил переписывал код в другом стиле.

Порядок: сначала свои правила, потом (если включены) стандартные.

Применение — одинаковое для обеих групп. Правила применять **по одному**, жадно:
1. применить правило → `count` затронутых функций;
2. если суммарный счёт затронутых функций не уменьшился → откат;
3. если уменьшился → проверка поведения → коммит или откат.
- Если правило дало выигрыш в одних функциях и проигрыш в других — применять его **точечно** (Rector умеет по файлам; для по-функционального — откатывать проигравшие функции через php-parser).
- Повторять проход по списку, пока за полный цикл нет улучшений (правила могут открывать друг другу возможности). Не больше `rector.max_passes` проходов.

Включение стандартных правил — **одной строкой** `enabled`. Список правил при этом всегда лежит в конфиге целиком (его пишет `opmin init`), пользователь его видит и правит, но включает/выключает всю группу одним флагом:
```yaml
rector:
  standard:
    enabled: false          # ← единственная строка, которую надо поменять, чтобы включить стандартные правила
    sets:
      - DEAD_CODE
      - EARLY_RETURN
      - CODE_QUALITY
      - UP_TO_PHP_TARGET    # раскладывается в LevelSetList под php.target
    rules:
      - Rector\CodeQuality\Rector\If_\SimplifyIfReturnBoolRector
      - Rector\CodeQuality\Rector\Assign\CombinedAssignRector
      - Rector\DeadCode\Rector\Assign\RemoveUnusedVariableAssignRector
      - Rector\EarlyReturn\Rector\If_\ChangeNestedIfsToEarlyReturnRector
      - Rector\CodeQuality\Rector\Class_\InlineConstructorDefaultToPropertyRector
    skip: []                # правила, которые исключить из наборов выше
```
- `enabled: false` — список игнорируется полностью, но остаётся в файле.
- Наборы раскладываются на отдельные правила и применяются по одному, как и всё в Stage A.
- CLI переопределяет конфиг на один запуск: `--with-standard-rector` / `--without-standard-rector`. Для разовых экспериментов: `--rector-rule=<FQCN>` (можно несколько раз) — запускает только указанные правила.
- Если в проекте есть свой `rector.php` — **не читать его** и не смешивать с нашими правилами (у проекта другие цели). `doctor` просто сообщает, что он есть.

Что идёт в список по умолчанию (на M3 проверить на playground, какие реально снижают опкоды; правила без выигрыша убрать из списка, который пишет `opmin init`; точные FQCN сверить с установленной версией Rector — правила иногда переименовывают и переносят):
- наборы `DEAD_CODE`, `EARLY_RETURN`, `CODE_QUALITY`;
- `LevelSetList::UP_TO_PHP_8x` под `php.target` (только правила, не меняющие семантику);
- `SimplifyIfReturnBoolRector`, `CombinedAssignRector`, `InlineConstructorDefaultToPropertyRector`, удаление лишних присваиваний и т.п.

Результат проверки (какие стандартные правила дают выигрыш на playground и сколько) записать в `docs/standard-rules.md` — это основа для рекомендованного списка и материал для README.

### Тесты самой тулзы на Testo

Все тесты opmin пишутся на **Testo** ([php-testo.github.io](https://php-testo.github.io/)), PHPUnit в проекте тулзы не используется вообще.

Структура:
```
tests/
  Unit/           # suite "unit": парсер дампа, конфиг, DynamicScopeDetector, генератор входов, сравнение значений
  Integration/    # suite "integration": count/optimize/check на фикстурах, верификатор на парах «до/после»
  Fixtures/       # фикстуры-ловушки и эквивалентные пары, дампы OPcache по версиям PHP
src/Rector/Rule/
  Fixture/        # *.php.inc для suite "rector" (см. ниже)
```
Конфиг Testo в корне — три suite: `unit`, `integration`, `rector` (последний — с `RectorTestingPlugin`).

Правила работы агента с Testo (это 0.x, у агента мало знаний о нём — **это главный риск, к нему отнестись серьёзно**):
- Версию `testo/*` фиксировать **точно**, все пакеты Testo — одной версии. Обновлять отдельным коммитом с прогоном всех тестов.
- **Перед первым тестом** прочитать документацию Testo целиком (быстрый старт, конфиг suite, атрибуты, ассерты, data providers, жизненный цикл, retry/expect exception, плагины) и исходники в `vendor/testo/`. Писать тесты по прочитанному, а не по аналогии с PHPUnit: ассерты, провайдеры данных и setup/teardown устроены иначе.
- Сразу после настройки — по одному smoke-тесту в каждом suite и **проверка, что он падает** при намеренной поломке. Тест, который не может покраснеть, хуже, чем отсутствие теста.
- Завести `docs/testing.md` — короткая шпаргалка «как у нас пишут тесты на Testo»: пример unit-теста, теста с data provider (для таблиц ловушек), интеграционного теста, Rector-фикстуры, как запустить один тест/suite, как снять покрытие. Агент заполняет её по мере выяснения и **сверяется с ней** при написании новых тестов — это лечит незнание фреймворка лучше всего.
- Фикстуры-ловушки верификатора оформлять через data provider: одна таблица `[название, код до, код после, ожидаемый вердикт]`, каждая строка — отдельный кейс в отчёте.
- Покрытие тестов самой тулзы: выяснить, как Testo собирает coverage (pcov/xdebug), и включить в CI. Если не поддерживается — записать в сводку.
- Если чего-то нужного в Testo нет или есть баг — **не** переходить на PHPUnit и не городить обёртки. Написать в сводке этапа: что именно, минимальный пример воспроизведения. Это кандидаты в issue/PR в репозиторий Testo.

Важно не путать: Testo — это то, **чем тестируется сама тулза**. Проекты пользователей могут быть на чём угодно (PHPUnit, Pest, Testo) — для них работают адаптеры тест-раннеров.

### Свои Rector-правила

Стандартные наборы Rector не делают оптимизаций, которые безопасны только при дополнительных условиях. Rector меняет код только там, где семантика гарантирована. Такие правила пишем сами, они живут в тулзе (`src/Rector/Rule/`) и участвуют в Stage A наравне со стандартными: применяются по одному, принимаются только при выигрыше в опкодах и после верификации.

Общие требования ко всем своим правилам:
- Правило **само проверяет условия безопасности** через типы PHPStan (Rector даёт доступ к `Scope` и `ObjectType`). Если условие не доказано — правило не срабатывает. Верификатор — вторая линия защиты, а не первая.
- Правило уважает флаги `DynamicScopeDetector` и `#[\Opmin\Ignore]`.
- Порог срабатывания (минимальное число повторов) — конфигурируемый параметр правила, по умолчанию подбирается **замером**: на M3 написать маленький бенч-скрипт, который для 1, 2, 3, 4 повторов компилирует оба варианта и показывает, с какого числа повторов вынос в переменную уменьшает `ops_opt` на текущем PHP. Значение по умолчанию — найденная точка окупаемости, с комментарием в коде, на какой версии PHP измерено.
- Имя новой переменной — производное от свойства/ключа (`$foo` для `$x->foo`, `$items` для `$data['items']`), без конфликтов с существующими переменными функции (проверять весь скоуп, включая `compact`-флаги — если флаг стоит, правило не срабатывает вообще).

#### 1. `ExtractRepeatedPropertyFetchRector` — реализовать первым

Выносит повторное чтение одного и того же свойства в локальную переменную:

```php
// до
if ($x->foo === null) {
    return;
}
$x->foo->bar();
$x->foo->baz();

// после
$foo = $x->foo;
if ($foo === null) {
    return;
}
$foo->bar();
$foo->baz();
```

Каждое `$x->foo` — отдельный `FETCH_OBJ_R`. После выноса — один `FETCH_OBJ_R` + присваивание, дальше работа с CV.

Условия безопасности (**все** должны выполняться):
- `$x` — локальная переменная или `$this`, не переприсваивается между первым и последним чтением.
- Свойство объявлено в классе (не динамическое), тип `$x` известен PHPStan точно (не `mixed`, не union с неизвестными классами).
- У класса и его родителей **нет** `__get` (для `$this` и `$x` с известным типом). Если класс не final — у наследников тоже может появиться `__get`, но объявленное свойство через `__get` не идёт, если оно инициализировано и видимо; при этом для **неинициализированного** типизированного свойства или `unset()`-нутого свойства `__get` вызовется. Поэтому для не-readonly свойств без гарантии инициализации — не срабатывать.
- Нет property hooks на свойстве (PHP 8.4+).
- Между чтениями **нет записей** в `$x->foo` и **нет `&$x->foo`** в функции.
- Одно из двух:
  - (а) свойство `readonly` — тогда вызовы методов между чтениями разрешены, значение измениться не может;
  - (б) свойство не readonly — тогда между чтениями **нет никаких вызовов** функций/методов/`new`/`include`, которые могли бы изменить `$x->foo` (включая вызовы методов на самом `$x->foo`: в примере выше `bar()` может через обратную ссылку сделать `$x->foo = null`). На практике (б) — это группы чтений внутри одного выражения или подряд идущих присваиваний без вызовов.
- Чтения в разных ветках (`if`/`else`) считаются, только если вынос ставится перед ветвлением и свойство читается в каждом пути выполнения хотя бы раз — иначе вынос добавит чтение в путь, где его не было (это тоже изменение поведения при `__get`, а без `__get` — просто лишний опкод).

В примере из заголовка правило сработает **только если `foo` — readonly**, потому что между чтениями вызываются `bar()`.

#### 2. `ExtractRepeatedArrayDimFetchRector`

То же для `$arr['key']` (повторное `FETCH_DIM_R` с одинаковым константным ключом):
- `$arr` — локальный массив (тип `array` по PHPStan), не `ArrayAccess`-объект (там `offsetGet` — вызов метода);
- между чтениями нет записей в `$arr` и `$arr['key']`, нет `&$arr`, нет передачи `$arr` по ссылке в функции;
- **warnings:** если ключ может отсутствовать, исходный код выдаёт warning `Undefined array key` на **каждое** чтение, а после выноса — один раз. Это изменение поведения (число warnings). Поэтому срабатывать, только если PHPStan доказывает наличие ключа (array shape) или чтение защищено `isset`/`array_key_exists` перед ним.

#### 3. `HoistLoopInvariantCountRector`

`for ($i = 0; $i < count($arr); $i++)` → `for ($i = 0, $n = count($arr); $i < $n; $i++)`:
- `$arr` не изменяется в теле цикла (нет записей, `[]=`, `unset`, `array_*` с ссылкой, передачи по ссылке, вызовов методов, если `$arr` — свойство);
- `count` разрешается в глобальную функцию (проверка затенения из 2.3);
- `$arr` — массив, не `Countable` (у `Countable::count()` может быть своя логика и побочные эффекты).

Статический счёт опкодов здесь почти не меняется (а может и вырасти на присваивание), а **исполненных** опкодов становится меньше в N раз. Поэтому это правило — первый кандидат для режима `--guard-perf` и динамического счёта. В статическом режиме принимать его, только если `ops_opt` не вырос; в отчёте отмечать как «выигрыш в исполненных, не в статических».

#### 4. `FullyQualifyGlobalCallsRector`

Переводит вызовы глобальных функций и константы внутри namespace в полностью квалифицированные (`strlen($s)` → `\strlen($s)`, `PHP_EOL` → `\PHP_EOL`). Скорее всего это самый жирный источник выигрыша: для части функций (`strlen`, `count`, `is_*`, `in_array`, `array_key_exists`, `defined`, `function_exists`, `chr`, `ord` и др.) компилятор генерирует спец-опкоды или вычисляет результат на этапе компиляции, а без FQN идёт обычный динамический вызов.
- Срабатывает только после проверки затенения из раздела 2.3 (индекс namespaced-функций и констант, детект php-mock / ClockMock / DnsMock).
- Стиль — конфигурируемый параметр: `style: backslash` (`\strlen`) или `style: use_function` (`use function strlen;` в шапке файла). По умолчанию — как уже принято в файле, если в нём есть хотя бы один пример; иначе `backslash`.
- Делает FQN для **всех** глобальных функций, не только «специальных»: даже без спец-опкода уходит рантайм-поиск в namespace. Выигрыш в опкодах при этом может быть нулевым — тогда изменение для этой функции не принимается (общее правило Stage A).

#### Ловушки для `traps/` к этим правилам

Добавить в `playground-seeds/traps/` и в фикстуры-ловушки верификатора (они должны **ловиться**: либо правило не срабатывает, либо верификатор откатывает):
- метод `bar()` через обратную ссылку переприсваивает `$x->foo`, свойство не readonly;
- класс с `__get`, который считает обращения/возвращает новый объект на каждое чтение;
- property hook `get` с побочным эффектом (сценарий только для PHP 8.4+);
- `$ref = &$x->foo;` и запись через `$ref` между чтениями;
- `unset($this->foo)` в конструкторе + `__get` (ленивая загрузка, как в Doctrine-прокси);
- `ArrayAccess`-объект вместо массива;
- отсутствующий ключ массива — разное число warnings;
- `count()` на массиве, который изменяется в теле цикла;
- `Countable` с побочным эффектом в `count()`.

И положительные кейсы, где правило **должно** сработать и дать выигрыш: readonly-свойство с вызовами методов между чтениями, `$this->config` в конструкторе-промоушене, массив с доказанным shape.

#### Тесты своих правил — на Testo

Тесты своих Rector-правил пишутся на **Testo** через пакет `testo/bridge-rector`, а не на стандартном `AbstractRectorTestCase` PHPUnit. Вся тулза тестируется на Testo (см. «Тесты самой тулзы на Testo»), это один из её suite.

Как устроено (по документации [php-testo.github.io/docs/bridge/rector](https://php-testo.github.io/docs/bridge/rector)):
- `composer require --dev testo/testo testo/bridge-rector`. Testo сейчас 0.x, API может меняться, поэтому **версию фиксировать точно** (не `^0.10`, а конкретную) и обновлять осознанно.
- На классе правила ставится атрибут `#[\Testo\Bridge\Rector\Testing\TestRectorFixtures('Fixture/ExtractRepeatedPropertyFetch')]` (путь относительно файла правила, можно несколько путей).
- Фикстуры — файлы `*.php.inc`: входной код, строка `-----`, ожидаемый результат. Если разделителя нет — правило не должно менять код (так оформлять все **отрицательные** кейсы и ловушки).
- Отдельный suite в конфиге Testo с плагином `RectorTestingPlugin`:
  ```php
  use Testo\Bridge\Rector\Testing\RectorTestingPlugin;

  return [
      new SuiteConfig(
          name: 'Rector',
          location: new FinderConfig(include: [__DIR__ . '/src/Rector']),
          plugins: [new RectorTestingPlugin()],
      ),
  ];
  ```
- Плагин сам находит все правила с атрибутом и гоняет каждую фикстуру как отдельный кейс.

Правила работы агента с Testo (он плохо знает этот фреймворк — у него мало обучающих данных по нему):
- **Перед первым тестом** прочитать документацию Testo (главную, раздел про suite-конфиг и страницу bridge/rector) и исходники `testo/bridge-rector` в `vendor/`. Не писать по памяти и не угадывать API по аналогии с PHPUnit.
- Сначала сделать **один** работающий smoke-тест на тривиальном правиле, убедиться, что он реально падает при неверной фикстуре (сломать ожидание и посмотреть на красный тест), и только потом писать остальные.
- Отдельно выяснить и задокументировать в `docs/testing.md`: как передаются **параметры конфигурируемого правила** (порог повторов) в тестах — в документации этого нет; как запускать один suite; как получить exit code для CI.
- Если что-то нужное не поддерживается в текущей версии Testo — не обходить костылями, а написать в сводке этапа, что именно не хватает (это кандидат в issue/PR в Testo).
- В `composer.json` скрипты: `composer test` (все suite), `composer test:rector` (только suite правил), `composer test:unit`, `composer test:integration`.

### Адаптеры тест-раннеров

Тесты проекта пользователя нельзя запускать одной жёстко прописанной командой: тулзе нужно не просто запустить тесты, а выбрать тесты, затрагивающие функцию, снять покрытие и понять результат. Это разное для разных раннеров.

Интерфейс `TestRunnerAdapter`:
```php
interface TestRunnerAdapter
{
    public static function detect(Project $project): bool;     // есть ли этот раннер в проекте
    public function runAll(): TestResult;                      // полный прогон
    public function runFiltered(array $testIds): TestResult;   // выборочный прогон
    public function collectCoverageMap(): CoverageMap;         // функция → тесты, которые её исполняют
}
```
`TestResult` — успех/провал, список упавших тестов, время, сырой вывод для отчёта. Результат парсить из машинного формата (JUnit XML), а не из текстового вывода.

Реализации:
- **PHPUnit:** JUnit через `--log-junit`, фильтр через `--filter` (регулярка по именам тестов, экранировать), покрытие через `--coverage-php` (сериализованный `CodeCoverage`, из него строится карта функция → тесты).
- **Pest:** работает поверх PHPUnit, те же флаги в основном работают, но имена тестов другие (описания, а не методы) — фильтр собирать по ним; проверить `--parallel`.
- **Testo:** выяснить по документации и исходникам, как получить машинный результат, фильтр и покрытие. Если чего-то нет (например, карты покрытия) — адаптер работает в урезанном режиме: только полный прогон, и `doctor` об этом предупреждает.
- **Fallback `command`:** просто команда из конфига, успех по exit code, без фильтра и покрытия.

Определение раннера: `opmin init` / `doctor` по `composer.json` (`require-dev`) и конфигам (`phpunit.xml(.dist)`, `tests/Pest.php`, конфиг Testo). Явное указание в конфиге:
```yaml
tests:
  runner: auto        # auto | phpunit | pest | testo | command
  command: null       # для runner: command, или чтобы переопределить бинарник
```
(Этот блок заменяет `commands.tests` и `commands.tests_filter` в конфиге.)

В playground добавить сценарий **`testo/`**: чистый PHP-проект с тестами на Testo + те же сиды. Проверяет адаптер Testo в режиме «проект».

### Stage B — LLM (Claude Code skill)

Сделать skill `.claude/skills/opcode-minimize/SKILL.md`. Процесс в скилле:

1. `opmin count --format=json` → взять топ-N функций по `ops_opt` (или все, изменённые в диапазоне).
2. Для каждой функции: показать модели исходник + дамп опкодов + гистограмму + флаги `DynamicScopeDetector` + ограничения из `readability` и `signatures` + список уже отклонённых попыток с причинами (чтобы модель не повторяла их).
3. Модель предлагает переписанную версию **только этой функции**.
4. `opmin apply-candidate` (подменяет тело функции через php-parser) → count → verify.
5. Принять, только если опкоды строго меньше и все проверки зелёные. Иначе откат, до K попыток на функцию.

Паттерны, которые скилл должен знать (каждый — проверять подсчётом, не верить на слово):
- FQN или `use function` для глобальных функций в namespace (`\strlen`, `\count`, `\is_array`, `\in_array`, `\array_key_exists`, `\is_null`, `\intval`, `\chr`, `\ord`, `\function_exists`, `\defined` и др.) — компилятор превращает их в спец-опкоды или вычисляет на этапе компиляции; без FQN идёт обычный `INIT_NS_FCALL_BY_NAME`.
- `isset($a[$k])` вместо `array_key_exists`, когда `null` в значениях невозможен (это **семантическое** условие — проверять!).
- Константные выражения → `const`, чтобы оптимизатор сворачивал их.
- Убрать временные переменные, используемые один раз.
- Ранний `return` вместо вложенных `if/else`.
- `static fn` для замыканий, не использующих `$this`.
- `===` вместо `==` только там, где типы гарантированы.
- Интерполяция vs конкатенация (ROPE-опкоды) — мерить, не угадывать.
- Вынос инвариантов из циклов (опкодов в функции может не стать меньше, но исполненных — станет; см. «метрика» ниже).

Жёсткие запреты для скилла: не менять публичную сигнатуру, порядок вызовов с побочными эффектами, порядок вычисления аргументов, обработку исключений, не убирать проверки типов, на которые завязано поведение.

### Код-стайл после каждого шага

Rector и LLM почти всегда ломают форматирование проекта (отступы, порядок `use`, переносы). Дифф без форматирования нечитаем, и PR с ним никто не примет.

- `opmin init` / `doctor` автоматически определяет форматтер проекта: `pint.json` → Laravel Pint, `.php-cs-fixer.php` / `.php-cs-fixer.dist.php` → PHP-CS-Fixer, `ecs.php` → ECS, `phpcs.xml` → PHPCBF. Результат пишется в конфиг:
  ```yaml
  commands:
    format: vendor/bin/pint {files}     # {files} — подставляются изменённые файлы
  ```
- После каждого применённого изменения (до подсчёта опкодов и проверки) прогонять форматтер **только по изменённым файлам**.
- После форматирования — повторно `php -l`. Форматтер тоже может изменить код (например, PHP-CS-Fixer с рискованными правилами вроде `native_function_invocation` сам делает FQN!). Поэтому опкоды считаются **после** форматирования, а изменения форматтера попадают в тот же шаг и проходят ту же проверку поведения.
- Если форматтера нет — `--format=none`, и тулза старается сохранить исходное форматирование: использовать **format-preserving printing** php-parser (`Parser` с сохранением токенов + `PrettyPrinter\Standard::printFormatPreserving()`), а не перепечатывать весь файл. Это требование и для режима с форматтером: печатаем format-preserving, форматтер добивает остальное. Цель — дифф затрагивает только реально изменённые строки.

### Читаемость: не принимать изменения, которые не стоят того

Минимальное число опкодов и читаемый код — разные цели. Без ограничений тулза с удовольствием сделает из понятного метода нечитаемую кашу ради −2 опкодов.

- **Порог выигрыша:** изменение принимается, только если выигрыш ≥ `readability.min_gain` опкодов **и** отношение выигрыша к размеру диффа (изменённые строки) ≥ `readability.min_gain_per_line`.
  ```yaml
  readability:
    min_gain: 1               # минимальный выигрыш в опкодах для принятия
    min_gain_per_line: 0.5    # опкодов на изменённую строку
    max_cyclomatic_increase: 0  # нельзя повышать цикломатическую сложность
    max_nesting_increase: 0     # нельзя увеличивать вложенность
    forbid_patterns:          # что LLM-стадии запрещено вносить
      - nested_ternary
      - assignment_in_condition
      - goto
  ```
- Цикломатическая сложность и глубина вложенности считаются через php-parser до/после. Рост — откат, даже при выигрыше в опкодах.
- **Интерактивный режим** `opmin optimize --review`: каждое изменение показывается как дифф функции + «−N опкодов, правило X, проверки: tests ✓, diff-tested 96% ✓», пользователь жмёт `y/n/a(всё это правило)/q`. Решения «отклонить» запоминаются в `opmin.baseline.yaml` (`rejected: [{function, rule}]`) и не предлагаются повторно.
- Неинтерактивный режим (CI, Claude Code) применяет всё, что прошло пороги.

### Игнорирование кода

Пользователь должен иметь возможность сказать «вот это не трогать»:
- Атрибут `#[\Opmin\Ignore]` на функции/методе/классе (класс атрибута поставляется в пакете-обёртке; если пакет не установлен в проект — атрибут всё равно распознаётся по имени через php-parser, класс в рантайме не нужен, PHP атрибуты не валидирует до `newInstance()`).
- Комментарий `// @opmin-ignore` перед функцией или `@opmin-ignore` в docblock — для тех, кто не хочет зависимость.
- Точечно по правилу: `#[\Opmin\Ignore(rules: ['fqn'])]` / `@opmin-ignore fqn,isset`.
- В конфиге:
  ```yaml
  ignore:
    paths: [src/Legacy, database/migrations]
    functions: ['App\Foo\Bar::hotPath', 'App\Utils\*']
  ```
- Сгенерированный код (`// @generated`, `@codeCoverageIgnore` не трогать — это другое) и файлы из `vendor/` игнорируются всегда.

## Модуль 4. CI-guard: `opmin check`

Скорее всего это станет главной причиной, почему тулзу будут ставить в проекты: не оптимизировать разово, а **не давать опкодам расти**.

### Baseline-файл

`opmin baseline` снимает текущий счёт и пишет `opmin.baseline.json` (коммитится в репозиторий):
```json
{
  "php": "8.3.12",
  "opmin": "1.2.0",
  "optimizer_hash": "a1b2c3",
  "functions": {
    "App\\Service\\Price::calculate": { "ops": 42, "file": "src/Service/Price.php" },
    "App\\Service\\Price::{closure:57}": { "ops": 7 }
  }
}
```
- Ключ функции стабильный: FQN класса + метод. Замыкания — по родительской функции + порядковому номеру замыкания в ней (не по номеру строки — строки сдвигаются при любом изменении файла).
- Формат детерминированный (ключи отсортированы), чтобы дифф baseline в PR был читаемым.

### `opmin check`

- По умолчанию — только файлы, изменённые относительно базовой ветки: `--base=origin/main` (через `git diff --name-only`). `--all` — весь проект.
- Для каждой изменённой функции сравнивает с baseline:
  - выросли опкоды больше чем на `check.tolerance` → **ошибка**, exit code 1;
  - уменьшились → сообщение «обнови baseline» (`--update-baseline` делает это сам);
  - новая функция → предупреждение, если превышает `check.max_ops_new_function` (опционально).
- Вывод в форматах: `table`, `json`, `github` (аннотации `::error file=...,line=...::` прямо в PR), `gitlab` (Code Quality JSON), `checkstyle`.
- Режим `--suggest`: для выросших функций запустить Rector-стадию в dry-run и показать, какое правило вернуло бы опкоды обратно.
- Если версия PHP / хэш оптимизатора в baseline не совпадает с текущими — не сравнивать, а сообщить, что baseline надо пересобрать на этой версии (exit code 2, отдельный от «опкоды выросли»).

```yaml
check:
  tolerance: 0                 # на сколько опкодов можно вырасти
  max_ops_new_function: null   # лимит для новых функций, null — без лимита
```

Готовые примеры для README: GitHub Actions workflow и `.gitlab-ci.yml` с Docker-образом.

## Безопасность режима git-пакета

`composer install` и запуск тестов чужого пакета = исполнение чужого кода на машине пользователя.

- `composer install --no-scripts --no-plugins` по умолчанию. Если без скриптов пакет не собирается — сообщить и предложить `--allow-scripts` явно.
- По умолчанию для режима git-пакета, если доступен Docker, тулза **сама перезапускает себя в контейнере** (`--no-docker`, чтобы отключить). Контейнер: без сети после установки зависимостей (`--network=none` на этапе тестов), read-only всё, кроме workspace, лимиты CPU/RAM.
- Без Docker — предупреждение перед запуском тестов чужого кода с подтверждением (`--yes` для неинтерактивного режима).
- Workspace клона — во временной директории с уникальным именем, удаляется после прогона (кроме `runs/` с отчётом и патчем, которые копируются в текущую директорию).

## Две версии PHP: оркестратор и харнесс

Решение: **код тулзы (оркестратор) — PHP 8.3+**, исполняется во встроенном PHP бинарника (или на PHP пользователя для PHAR). **Харнесс — PHP 8.1+**, исполняется под PHP проекта (`php.binary`). Поддерживаемые версии PHP проектов пользователей — **8.1–8.5**.

| Что | Где исполняется | Минимальная версия |
|---|---|---|
| Оркестратор: CLI, конфиг, Rector, генерация входов (`property-testing-core`), шринкинг, сравнение результатов, отчёты | встроенный PHP бинарника / PHP для PHAR | 8.3 |
| Подсчёт опкодов (`opcache_compile_file` + дамп) | `php.binary` | 8.1 |
| **Харнесс** дифф-тестера | `php.binary` | **8.1** |
| Тесты и PHPStan проекта | `php.binary` | как у проекта |

### Харнесс

Маленький изолированный кусок кода в `harness/` (отдельно от `src/`), который запускается под PHP проекта и делает **только** то, что обязано происходить внутри PHP проекта: загрузить автолоадер проекта, построить аргументы и объекты, вызвать старую и новую версию функции, перехватить результат, исключения, вывод, warnings, побочные эффекты, снять покрытие — и отдать всё это наружу в нормализованном виде. Вся логика «что генерировать» и «равны ли результаты» — в оркестраторе.

Жёсткие требования к харнессу:
- **PHP 8.1 синтаксис и стандартная библиотека 8.1.** Никаких `readonly`-классов, typed class constants, `#[\Override]`, `json_validate()` и т.п. Проверка в CI: `php -l` на PHP 8.1 + PHPStan/Psalm с `phpVersion: 80100` только по `harness/`.
- **Ноль composer-зависимостей.** Харнесс не может тащить `vendor/` тулзы в процесс проекта (конфликты классов). Только свой код, в своём уникальном namespace (`Opmin\Harness\…`), без автолоадера тулзы: один файл-бутстрап `harness/bootstrap.php`, который подключает остальные файлы харнесса через `require`.
- Харнесс **не скоупится Box-ом** отдельно — он и так ни от чего не зависит, но лежит в бинарнике/PHAR как ресурс и **извлекается во временную директорию** перед запуском (`php.binary` не умеет читать файлы из PHAR внутри micro-бинарника напрямую). Извлечённая копия кешируется по хэшу версии opmin.
- Маленький и простой: цель — сотни строк, не тысячи. Всё сложное — в оркестраторе.

### Протокол оркестратор ↔ харнесс

- Харнесс — **долгоживущий воркер**: оркестратор запускает `php.binary harness/worker.php` (с нужными `-d` для покрытия и `memory_limit`), общается по stdin/stdout построчно **JSON Lines** (одна команда — одна строка, один ответ — одна строка). Старт процесса PHP на каждый вход сделал бы шринкинг и фаззинг неприемлемо медленными.
- Пул воркеров по числу ядер; воркер перезапускается после N вызовов, после таймаута, фатала или OOM (факт таймаута/фатала — это тоже результат, который сравнивается).
- Команды (примерный набор, агент уточняет на M2):
  - `load` — подключить автолоадер проекта и файл с двумя версиями функции (`__opmin_orig\…` и новая);
  - `call` — вызвать функцию (старую или новую) с аргументами, вернуть результат;
  - `snapshot` / `restore` — снапшот статических свойств и `static`-переменных для изоляции вызовов;
  - `coverage_start` / `coverage_stop` — покрытие (pcov или xdebug — что есть в `php.binary`);
  - `ping` / `shutdown`.
- **Аргументы передаются не как PHP-объекты, а как «рецепты»** — это ключевое решение. Объект нельзя сгенерировать в процессе на PHP 8.4 и передать в процесс на PHP 8.1. Поэтому генератор в оркестраторе выдаёт описание:
  ```json
  {"type": "int", "value": 5}
  {"type": "string", "value": "abc"}
  {"type": "float", "value": "-0.0"}
  {"type": "array", "items": [[{"type":"string","value":"k"}, {"type":"null"}]]}
  {"type": "object", "class": "App\\Money", "via": "ctor", "args": [ ... ]}
  {"type": "object", "class": "App\\Money", "via": "props", "props": {"amount": {...}}}
  {"type": "mock", "interface": "App\\Clock", "returns": {"now": [ ... ]}}
  {"type": "ref", "id": 3}
  ```
  Харнесс по рецепту строит значение (конструктор, `newInstanceWithoutConstructor` + рефлексия, генерация мока). `ref` — для одного и того же объекта в нескольких аргументах (идентичность важна). Float — строкой, чтобы не терять `-0.0`, `NAN`, `INF` и точность в JSON.
- **Моки генерирует харнесс** (кодогенерация анонимного класса, реализующего интерфейс, с журналом вызовов) — по рецепту `mock` из оркестратора. Журнал вызовов возвращается вместе с результатом.
- **Результат возвращается тоже нормализованным описанием**, а не сериализованным PHP: тип, значение, для объектов — класс и рекурсивно свойства (через рефлексию, с защитой от циклов через `ref`), исключение (класс, сообщение, код, `previous` рекурсивно), буфер вывода, список warnings (уровень, текст), состояние by-ref аргументов, состояние `$this` после вызова, журнал моков, затронутые глобалы, покрытые строки. Сравнение по правилам 2.1–2.5 делает оркестратор над этими описаниями.
- Подмены времени и рандома (2.5) — namespaced-функции, которые харнесс подключает **до** загрузки кода функции; фиксированные значения задаёт оркестратор в `load`.

### Как это стыкуется с property-testing-core

- Генераторы core в оркестраторе порождают **рецепты**, а не значения (свои `Arbitrary`, которые на выходе дают описание из протокола выше). Скаляры и массивы — прямо из генераторов core; объекты и моки — свои генераторы рецептов.
- Свойство для core: «рецепт → вызов `old` через харнесс → вызов `new` через харнесс → описания результатов эквивалентны». То есть callback свойства делает два round-trip к воркеру.
- Шринкинг core работает над рецептами — минимальный контрпример получается сам; в отчёт и в сгенерированный тест идёт уже сжатый рецепт, который адаптер тест-раннера превращает в PHP-код теста.

### Насколько это затратно

Умеренно, и это стоит делать: основная работа — протокол, рецепты и нормализация результатов. Всё это всё равно нужно (без нормализации нельзя сравнивать объекты и исключения), просто живёт на другой стороне процесса. Новое по сравнению с «всё в одном процессе» — только JSON-протокол и пул воркеров. Взамен — поддержка проектов на 8.1–8.2 и полная изоляция кода тулзы от кода пользователя (бонус: падение или `exit()` в коде пользователя не валит тулзу).

## Важное замечание по метрике

Статический счёт опкодов ≠ скорость. Опкод внутри цикла на 10k итераций весит больше, чем 5 опкодов вне его, а `in_array` — один опкод, внутри которого линейный поиск. Поэтому:

- Основная метрика — **статические опкоды после оптимизатора** (как в ТЗ).
- Флаг `--guard-perf`: для функций с бенчмарками (phpbench) или для дифференциальных прогонов замерять время; если стало медленнее больше чем на X% — откат даже при выигрыше в опкодах.
- Задел на будущее (не в MVP): динамический счёт исполненных опкодов через `zend_execute_ex`-хук/расширение — тогда оптимизировать можно «исполненные опкоды на типовых входах».

## Конфиг `opmin.yaml`

Только YAML, PHP-конфигов нет. Механизм — DTO-классы с атрибутами из обвязки dload (см. «Основа проекта»), источник — `symfony/yaml`. Неизвестные ключи и неверные типы дают понятную ошибку с путём ключа. Любой ключ можно переопределить переменной окружения и опцией CLI. JSON Schema для автодополнения в IDE генерируется из DTO. Поиск конфига: `--config=` → `opmin.yaml` → `opmin.yaml.dist` в корне проекта. `opmin init` генерирует файл с дефолтами и комментариями.

Полный конфиг со всеми ключами и значениями по умолчанию (это же — содержимое, которое генерирует `opmin init`, с комментариями):

```yaml
paths: [src]
exclude: [vendor, tests]

php:
  binary: php            # каким PHP компилировать и считать, должен совпадать с продом
  target: '8.3'          # по умолчанию из composer.json (config.platform.php → require.php)

tests:
  runner: auto           # auto | phpunit | pest | testo | command
  command: null          # для runner: command, или чтобы переопределить бинарник

commands:
  phpstan: vendor/bin/phpstan analyse --no-progress --error-format=json
  format: vendor/bin/pint {files}    # null — без форматтера, только format-preserving печать

rector:
  custom_rules:          # свои правила opmin — включены по умолчанию; false — отключить правило
    Opmin\Rector\Rule\FullyQualifyGlobalCallsRector: {}
    Opmin\Rector\Rule\ExtractRepeatedPropertyFetchRector: { min_reads: auto }
    Opmin\Rector\Rule\ExtractRepeatedArrayDimFetchRector: { min_reads: auto }
    Opmin\Rector\Rule\HoistLoopInvariantCountRector: {}
  standard:              # стандартные правила Rector
    enabled: false       # одна строка: true — включить всю группу
    sets: [DEAD_CODE, EARLY_RETURN, CODE_QUALITY, UP_TO_PHP_TARGET]
    rules:
      - Rector\CodeQuality\Rector\If_\SimplifyIfReturnBoolRector
      - Rector\CodeQuality\Rector\Assign\CombinedAssignRector
      - Rector\DeadCode\Rector\Assign\RemoveUnusedVariableAssignRector
      - Rector\EarlyReturn\Rector\If_\ChangeNestedIfsToEarlyReturnRector
      - Rector\CodeQuality\Rector\Class_\InlineConstructorDefaultToPropertyRector
    skip: []
  max_passes: 3

verification:
  warnings: strict             # strict | allow_removal
  min_branch_coverage: 90      # %, ниже — функция unverified
  coverage_driver: auto        # auto | xdebug | pcov
  random_inputs: 200
  fuzz_time_ms: 2000           # лимит coverage-guided добора на функцию
  seed: 42
  float_tolerance: 1.0e-12     # 0 — побитовое сравнение
  call_timeout_ms: 1000
  memory_limit: 256M
  allow_unverified: false      # менять функции без доказанного поведения

readability:
  min_gain: 1
  min_gain_per_line: 0.5
  max_cyclomatic_increase: 0
  max_nesting_increase: 0
  forbid_patterns: [nested_ternary, assignment_in_condition, goto]

signatures:
  phpdoc: true
  native_types: non_overridable    # none | non_overridable | all
  public_api: false

ignore:
  paths: []
  functions: []

llm:
  top_n: 20
  attempts_per_function: 3

guard_perf:
  enabled: false
  max_regression_percent: 5

check:
  tolerance: 0
  max_ops_new_function: null
  base_ref: origin/main

cache:
  dir: .opmin-cache      # добавить в .gitignore при init
```

## Поставка

**Основной способ выпуска — статический бинарник. PHAR — опциональный.**

Тулза тащит Rector, php-parser и Symfony-компоненты, поэтому в любом варианте код зависимостей **скоупится** (Box + PHP-Scoper): бинарник собирается из того же скоупленного PHAR (`spc micro:combine`), так что требование одно для обоих форматов. Без скоупинга классы `PhpParser\*`/`Symfony\*` тулзы столкнутся с версиями из `vendor/` проекта, когда мы загружаем его автолоадер (Rector, анализ типов). Отдельно проверить, что должно оставаться нескоупленным (то, что видит проект: атрибут `#[\Opmin\Ignore]`, интерфейсы, которые реализует код пользователя, если такие появятся).

**1. Статический бинарник — основной.**
- Сборка через [static-php-cli](https://static-php.dev) по образцу CI dload: скоупленный PHAR + `micro` → один исполняемый файл, PHP на машине для **запуска** тулзы не нужен.
- Платформы: linux-x86_64, linux-aarch64 (статически, musl — работает на любом дистрибутиве), macos-x86_64, macos-arm64. Windows — после MVP.
- Встроенный PHP — последней стабильной версии (8.4/8.5), на нём работают оркестратор, Rector, генерация входов, отчёты.
- **Встроенный PHP никогда не используется для того, что зависит от версии прода:** подсчёт опкодов, харнесс дифф-тестера, тесты и PHPStan проекта — всегда подпроцессом через `php.binary` (по умолчанию — `php` из `PATH`). Если `php.binary` нет — команды, которым он нужен, падают с понятным сообщением; `count` и `optimize` без него не работают, `doctor` это показывает первым пунктом.
- Набор расширений для `spc`: только то, что нужно оркестратору (`tokenizer`, `mbstring`, `ctype`, `phar`, `json`, `pcntl`, `posix`, `iconv`, `filter`, плюс то, что потребуют оставшиеся зависимости — проверить по `composer-require-checker`). OPcache в бинарник **не** нужен.
- Релизы: GitHub Releases, бинарник на каждую платформу + `sha256sum.txt` + подпись (cosign или GPG).
- Самообновление: `opmin self-update` (скачивает релиз под текущую платформу, проверяет checksum и подпись). `--check` — только сообщить о новой версии.
- Установка (в README именно этот способ первым):
  - скрипт: `curl -fsSL https://.../install.sh | sh` — определяет ОС и архитектуру, качает в `~/.local/bin` (или `--dir`), проверяет checksum;
  - **через dload** — естественный путь, раз каркас из него: добавить opmin в реестр dload (PR в `php-internal/dload`, `resources/software.json`), тогда в проекте `dload.xml` фиксирует версию opmin, и `vendor/bin/dload get` качает нужный бинарник. Это и есть рекомендуемый способ **зафиксировать версию тулзы на проект** без конфликтов в composer;
  - вручную из GitHub Releases.

**2. PHAR — опциональный.**
- Тот же скоупленный PHAR, из которого собирается бинарник, публикуется в релизе отдельным файлом. Нужен тем, кто хочет запускать тулзу на своём PHP (8.3+).
- `phive install opmin`.
- **Composer-пакет-обёртка** `<vendor>/opmin`: отдельный репозиторий, в котором лежит только PHAR и `bin/opmin`, без зависимостей в `require` (как `phpstan/phpstan`). `composer require --dev <vendor>/opmin` работает без конфликтов. В README — как альтернативный способ, не первый.

**3. Docker-образ (для CI и git-пакетов).**
- Внутри — бинарник opmin + **PHP нужной версии прода** с OPcache (JIT выключен) как `php.binary`, pcov, git, composer. Теги: `ghcr.io/<vendor>/opmin:<version>-php8.1` … `-php8.5`.
- Важно: **число опкодов зависит от версии PHP**. Отчёты, снятые на 8.2 и на 8.4, не сравнимы. Поэтому в отчёт и в JSON писать `PHP_VERSION` и хэш настроек оптимизатора, а `diff` отказывается сравнивать прогоны с разной версией.

**Локальная vs глобальная установка.**
- Бинарник по умолчанию **глобальный** (в `PATH`) — подходит для всех режимов, включая git-пакеты и голые файлы.
- Зафиксировать версию на проект: `dload.xml` (рекомендуется) или composer-обёртка с PHAR.
- В проекте может лежать `.opmin-version` (или `opmin.yaml: requires: '^1.2'`) — глобальный бинарник проверяет совпадение и при несовпадении говорит, какую версию поставить (`opmin self-update --to=1.2.3`).
- Если глобальный `opmin` запущен внутри проекта, где есть локальный `vendor/bin/opmin` (обёртка) или скачанный через dload бинарник, — передать управление локальному, чтобы версии не расходились.
- **Docker** — рекомендуемый способ для git-пакетов: решает и версию PHP пакета (`require.php` в его `composer.json`), и нужные пакету расширения. В режиме git-пакета `opmin` проверяет `require.php` и `ext-*` пакета против `php.binary` и при несовпадении останавливается с подсказкой взять нужный Docker-тег.

**4. Skill для Claude Code едет внутри тулзы.**
- `opmin init` создаёт `opmin.yaml` и кладёт `.claude/skills/opcode-minimize/SKILL.md` в проект (с флагом `--no-skill`, если не нужен).
- Глобальная установка: `opmin skill:install --global` кладёт skill в `~/.claude/skills/opcode-minimize/`, чтобы он был доступен в любой директории, включая временный клон git-пакета.
- `opmin skill:update` обновляет skill до версии, соответствующей установленному opmin (skill лежит внутри бинарника/PHAR). В SKILL.md прописана версия, skill проверяет, что `opmin --version` совпадает.
- Позже можно оформить как плагин Claude Code с маркетплейсом, но в MVP не надо.

**5. `opmin doctor`.** Первое, что запускает пользователь и CI: проверяет, что `php.binary` найден и его версия поддерживается харнессом (8.1+), что OPcache в нём доступен в CLI (`zend_extension` загружен), `opcache_compile_file` работает, есть git, тесты и PHPStan запускаются по командам из конфига, версия PHP совпадает с `php.target`. Выводит, что не так и как починить.

## Версии PHP и инструментов

Разделять **runtime PHP** (на чём запущен инструмент) и **target PHP** (под какую версию анализируем код):

| Что | От runtime PHP | От target PHP | Чья версия |
|---|---|---|---|
| Подсчёт опкодов | **Зависит напрямую** | — | runtime = прод |
| Тесты, дифф-тестирование | **Зависит** (код исполняется) | — | runtime = прод |
| Rector | Нет (свой парсер) | Да: какие правила применимы | **Своя, вшитая в PHAR**, зафиксирована версией opmin |
| PHPStan | Почти нет | Да: стабы встроенных функций, доступные фичи | **Проекта**, если есть; иначе вшитая |

Правила:
- `php.target` из `opmin.yaml` (по умолчанию из `require.php`/`config.platform.php` в `composer.json`) **явно передаётся** в Rector (`phpVersion`) и PHPStan (`phpVersion`). Не полагаться на автоопределение — PHPStan без настройки берёт версию из runtime, и сигнатуры встроенных функций могут не совпасть с продом.
- Rector всегда наш, а не проектный: список правил-кандидатов привязан к его версии, иначе одно и то же правило в разных версиях делает разное.
- PHPStan проектный, потому что у проекта свой конфиг, baseline и расширения (Larastan и т.п.). Нам нужна не абсолютная оценка, а «не появилось новых ошибок» — сравнение до/после одной и той же версией.
- В отчёт пишутся версии: PHP runtime, `php.target`, Rector, PHPStan, opmin. `diff` и повторный прогон предупреждают, если что-то из этого изменилось.

## Отчёт

`runs/<timestamp>/report.md` + `report.json`:
- общий итог: опкоды до/после, %;
- по функциям: до → после, какой шаг дал выигрыш (имя Rector-правила или «LLM»), статус верификации (`tests`, `diff-tested`, `unverified`);
- список отклонённых изменений с причиной (не уменьшило опкоды / упали тесты / diff-тест нашёл расхождение — с контрпримером на входе / не прошло порог читаемости / функция помечена динамическими флагами);
- по каждой функции: покрытие дифф-тестами, покрытие тестами проекта, флаги `DynamicScopeDetector`;
- контрпримеры — как готовые тесты в формате тест-раннера проекта в `runs/<ts>/counterexamples/`;
- окружение прогона: версии PHP, opmin, Rector, PHPStan, хэш настроек оптимизатора.

## Учесть при реализации

### Трейты, наследование, особые случаи подсчёта

- **Трейты:** метод трейта компилируется в файле трейта и копируется в использующие классы в рантайме. Считать **один раз, по месту определения** (`TraitName::method`). В отчёте для класса, использующего трейт, не дублировать. Если класс переименовывает метод трейта (`use T { foo as bar; }`) — всё равно считается в трейте.
- **Абстрактные методы и методы интерфейсов** — 0 полезных опкодов, в отчёт не попадают.
- **Enum-методы, `readonly`-классы, first-class callable syntax (`strlen(...)`)** — должны корректно разбираться парсером дампа; добавить в фикстуры.
- **Property hooks (PHP 8.4)** — в дампе выглядят как отдельные функции (`Class::$prop::get`); поддержать, если runtime 8.4+.
- **Анонимные классы** — ключ: родительская функция + порядковый номер `class@anonymous` в ней.
- **Код вне функций** (`$_main` файла) — считать отдельно и показывать как `file.php::<main>`, но по умолчанию не оптимизировать (там обычно объявления, конфиги, роуты).
- Файлы с синтаксисом выше runtime PHP (`php.target` > runtime) — `opcache_compile_file` упадёт. `doctor` должен ловить это до начала работы.

### Скорость самой тулзы

На проекте в несколько тысяч файлов наивная реализация будет работать часами. Требования:
- **Параллельная компиляция:** пул процессов (`symfony/process` или `amphp/parallel`), размер пула по умолчанию — число ядер. Один процесс компилирует пачку файлов (не по процессу на файл — старт PHP ~20–50 мс), дамп разделяется по маркерам. Важно: при компиляции пачки в одном процессе нужно убедиться, что результат не отличается от компиляции по одному (классы из ранее скомпилированных файлов могут влиять на оптимизатор). Проверить на фикстурах; если влияет — изолировать по файлу.
- **Кеш подсчёта:** ключ = `sha256(содержимое файла) + PHP_VERSION + хэш ini-настроек opcache + версия opmin`. Хранить в `.opmin-cache/`. Повторный `count` на неизменённом проекте должен занимать секунды.
- **Кеш индекса** namespaced-функций, AST и флагов `DynamicScopeDetector` — по тому же принципу.
- **Тесты проекта — выборочно:** через coverage-карту (один раз прогнать тесты с покрытием на старте, сохранить маппинг «функция → тесты») запускать только затронутые тесты на каждом шаге. Полный прогон — один раз в конце. Если coverage-драйвера нет — полный прогон каждый раз и предупреждение в `doctor`, что будет медленно.
- **Батчинг Rector:** одно правило прогоняется по всем целевым файлам за один запуск Rector, а не по файлу.
- Прогресс-бар (`symfony/console` ProgressBar) с ETA на каждой стадии; `-v` выводит, что сейчас делается.
- **Возобновление:** если прогон прервали (Ctrl+C, упало), `opmin optimize --resume` продолжает с последнего принятого шага по `runs/<ts>/state.json`.

### Тестирование самой тулзы

- **Unit-тесты** парсера дампа на зафиксированных дампах для каждой минорной версии PHP (формат дампа немного меняется между версиями).
- **Фикстуры-ловушки** для верификатора — набор пар «до/после», где «после» **меняет поведение**, и каждая должна быть поймана. Минимум:
  - `==` → `===` на смешанных типах;
  - `array_key_exists` → `isset` при `null`-значениях;
  - `$a['x']` → `$a['x'] ?? null` (исчезает warning);
  - FQN `\time()` при зарегистрированном ClockMock;
  - удаление «неиспользуемой» переменной при `compact()`;
  - `isset($obj->x)` → `$obj->x !== null` на объекте с `__get`/`__isset`;
  - добавление `int` к параметру без `strict_types` при вызове со строкой `'5'`;
  - изменение порядка двух вызовов мока;
  - изменение поведения `static`-переменной на втором вызове;
  - ветка, срабатывающая только на «магической» строке из тела функции (проверка, что добор входов из литералов её находит);
  - `-0.0` vs `0.0`.
  Тест верификатора: **все** ловушки отклонены, а набор заведомо эквивалентных пар — **все** приняты (иначе верификатор просто отклоняет всё подряд).
- **Матрица CI:** оркестратор — PHP 8.3, 8.4, 8.5; харнесс и подсчёт опкодов (как `php.binary`) — PHP 8.1, 8.2, 8.3, 8.4, 8.5. Интеграционные тесты гоняют комбинации «бинарник + `php.binary` 8.1» и «бинарник + `php.binary` 8.5» как минимум. Linux; macOS — smoke-тест бинарника.
- **Smoke на реальных пакетах:** в CI раз в неделю прогонять `opmin optimize` на нескольких реальных пакетах (например, `symfony/string`, `nesbot/carbon`, `league/csv`) и проверять, что их **собственные** тесты остаются зелёными. Это лучший детектор ложноположительных «эквивалентных» изменений. Результаты (выигрыш в опкодах) — хороший материал для README.
- **Property-тесты самой тулзы** через `rasuvaeff/property-testing-testo` (`#[Property]`): особенно для компаратора значений (рефлексивность, симметричность, `-0.0`/`NAN`), парсера дампа (не падает на любом валидном PHP-коде из генератора), конфиг-лоадера.
- **Статический анализ самой тулзы:** Psalm (как в dload), тесты — Testo, мутационное тестирование верификатора через Infection + `testo/bridge-infection` (верификатор — критичная часть, MSI ≥ 80%). Если связка Infection + Testo в текущих версиях не заводится — не переписывать тесты на PHPUnit, а написать в сводке этапа, что именно не работает.

### Playground — ручное e2e-тестирование

Директория `playground/` в корне репозитория тулзы, **целиком в `.gitignore`**. Это песочница, где агент (и я) после каждого этапа гоняет тулзу руками в условиях, максимально близких к реальным, смотрит отчёты и дифы глазами. Автотесты это не заменяет — дополняет.

**Что коммитится, а что нет:**
- В гите: `playground-seeds/` (исходники сценариев: неоптимальный код, тесты, конфиги) и скрипт-генератор `bin/playground`.
- Не в гите: `playground/` — генерируется скриптом и может быть удалён и пересоздан в любой момент. В `.gitignore`: `/playground/`.

**Сценарии (каждый — поддиректория `playground/`):**

| Сценарий | Что внутри | Что проверяет |
|---|---|---|
| `laravel/` | Свежий Laravel (`composer create-project laravel/laravel`), в `app/Services/` подложены классы из сидов + PHPUnit-тесты к ним, Pint из коробки | Режим «проект»: автолоадер, тесты фреймворка, `HandleExceptions` (warning → исключение), Pint как форматтер, Larastan если поставлен |
| `symfony/` (опционально) | `symfony/skeleton` + те же сервисы | Другой фреймворк, `ErrorHandler`, PHP-CS-Fixer как форматтер |
| `vanilla/` | Голые `.php` файлы и поддиректории **без** `composer.json` и тестов: функции в namespace и без, классы, замыкания | Режим «голые файлы»: работа без автолоадера и тестов, только дифф-тесты, корректная пометка `unverified` |
| `vanilla-composer/` | Чистый PHP-проект с `composer.json`, PSR-4, PHPUnit, без фреймворка | Режим «проект» без фреймворка |
| `git-package/` | Локальный bare-репозиторий `git-package.git` (генерируется из сида, с тегами `v1.0.0`, `v1.1.0`) | Режим git-пакета: `opmin optimize file://$(pwd)/playground/git-package.git --ref=v1.1.0`, клон во временную директорию, `--no-scripts`, результат — ветка и `.patch` |
| `git-package-real/` (опционально) | Клон небольшого реального пакета по фиксированному тегу | То же на реальном коде |
| `testo/` | Чистый PHP-проект с `composer.json`, тесты на Testo | Адаптер Testo: запуск, фильтр, покрытие (или урезанный режим с предупреждением) |
| `traps/` | Код из фикстур-ловушек верификатора + проектные тесты, которые **намеренно** не ловят поломку | Проверка, что дифф-тестер ловит то, что пропускают слабые тесты |

**Сиды (`playground-seeds/`)** — общий набор неоптимального, но рабочего кода, который подкладывается в каждый сценарий (с поправкой на namespace):
- функции с очевидной выгодой: вызовы глобальных функций без FQN в namespace, вложенные `if` вместо раннего возврата, лишние временные переменные, `array_key_exists` на массивах без `null`;
- функции-ловушки: `compact()`, `static`-переменные, `__get`/`__isset`, `func_get_args()`, `array_key_exists` на массивах **с** `null`, вызов `time()` с ClockMock в тестах;
- методы с `private`/`public`-сигнатурами без типов (проверка правил `signatures`);
- замыкания, трейт, enum, анонимный класс (проверка подсчёта);
- побочные эффекты: запись в файл, лог, вызов сервиса через интерфейс (проверка моков и пометки side-effecting).

**Скрипт `bin/playground`** (PHP или bash, без зависимостей кроме composer/git):
```
bin/playground init [scenario...]   # создать сценарии (по умолчанию все обязательные)
bin/playground reset [scenario...]  # удалить и пересоздать с нуля (чистое состояние)
bin/playground run <scenario>       # прогнать полный цикл: doctor → count → optimize → check, с отчётом
bin/playground run --all            # по всем сценариям, сводная таблица
bin/playground php <ver> <cmd>      # запустить команду в Docker-образе нужной версии PHP (php:8.1-cli … php:8.4-cli)
```
- `init` для фреймворков использует кеш composer, чтобы не качать заново при каждом `reset`.
- После создания каждый сценарий — **git-репозиторий** (`git init`, начальный коммит), чтобы проверить режим «коммит на каждый шаг», `--dry-run` и откаты. Отдельно сценарий `vanilla/` создаётся **без** git — проверить режим отката из копии.
- `run` тулзу берёт из исходников (`bin/opmin`), а на этапе M7 — ещё и из собранного PHAR, и из Docker-образа, чтобы проверить все способы поставки.
- `run --all` печатает сводку: сценарий, опкоды до/после, принято/отклонено изменений, тесты сценария зелёные ли после оптимизации, найдены ли все ловушки в `traps/`.

**Правило для агента:** каждый этап M1–M8 (начиная с M1, когда есть что запускать) заканчивается прогоном `bin/playground run --all` (в объёме того, что уже реализовано на этом этапе) и коротким отчётом в сводке этапа: что увидел, что выглядит подозрительно. Тесты сценариев после `optimize` обязаны оставаться зелёными; ловушки в `traps/` — все отклонены. Если на playground нашлась проблема, которую не ловят автотесты, — сначала добавить автотест (фикстуру), потом чинить.

## Этапы и критерии приёмки

**M0 — каркас из dload и playground.** Обвязка dload перенесена по разделу «Основа проекта»: модули удалены, всё переименовано, конфиг переведён на YAML с тем же механизмом атрибутов, в Box добавлен PHP-Scoper, сборка PHAR и статического бинарника проходит в CI, `bin/opmin list` работает. Репозиторий, `composer.json`, CI с матрицей PHP, Testo настроен с тремя suite (`unit`, `integration`, `rector`), в каждом по одному smoke-тесту, который проверенно краснеет при поломке, всё запускается через `composer test` и в CI, `bin/opmin` с пустыми командами, `playground-seeds/`, `bin/playground init/reset` создают все обязательные сценарии, тесты сценариев зелёные на исходном коде. `/playground/` в `.gitignore`.

**M1 — `count`.** На фикстуре из ~10 функций (включая методы, статические методы, замыкания, анонимные классы, enum-методы, трейты, функции в namespace) счёт совпадает с ручной проверкой дампа OPcache. Есть тесты парсера дампа для каждой минорной версии PHP из матрицы. Работает кеш: повторный запуск без изменений — без перекомпиляции.

**M2 — верификация.** Все фикстуры-ловушки из раздела «Тестирование самой тулзы» отклоняются, все эквивалентные пары принимаются. Сравниваются: return, исключения, вывод, warnings/notices, by-ref аргументы, состояние объекта, журнал вызовов моков. Работают покрытие дифф-тестов, добор входов из литералов, детерминизм (время, рандом, float, объекты). `DynamicScopeDetector` ставит флаги на всех конструкциях из таблицы. Адаптеры тест-раннеров PHPUnit, Pest, Testo и `command` работают на сценариях playground (`laravel/`, `vanilla-composer/`, `testo/`). Харнесс — отдельный воркер на PHP 8.1+ без зависимостей, протокол JSON Lines с рецептами аргументов; все ловушки ловятся при `php.binary` = 8.1 и = 8.5 (`bin/playground php 8.1 …`); шринкинг выдаёт минимальный контрпример; `exit()`/фатал в коде пользователя не валит оркестратор.

**M3 — Rector-стадия + форматирование + читаемость.** На фикстуре суммарный счёт уменьшается, каждое принятое правило — отдельный коммит, правила без выигрыша откатываются. После каждого шага работает форматтер проекта, дифф затрагивает только изменённые строки. Пороги читаемости отклоняют изменения, повышающие сложность. Проверка затенения FQN работает. Четыре своих правила реализованы (первым — `ExtractRepeatedPropertyFetchRector`, затем `FullyQualifyGlobalCallsRector`), точка окупаемости `min_reads` измерена и записана, тесты правил на Testo зелёные и **падают** на сломанной фикстуре, все ловушки к правилам не срабатывают, положительные кейсы дают выигрыш. По умолчанию работают только свои правила; стандартные лежат в конфиге списком и включаются одной строкой `enabled: true` или флагом, по ним заполнен `docs/standard-rules.md`.

**M4 — skill.** SKILL.md + команда `apply-candidate`. Claude Code проходит по топ-функциям фикстуры и даёт дополнительный выигрыш поверх Rector без падений проверок. В промпт для каждой функции передаются флаги динамических конструкций и ограничения из `readability`.

**M5 — отчёт, `--review`, `--resume`, `--guard-perf`, `#[Ignore]`.**

**M6 — `opmin check` и baseline.** Падает в CI при росте опкодов, вывод в форматах `github`/`gitlab`/`checkstyle`, работает режим «только изменённые файлы» относительно базовой ветки. Примеры workflow для GitHub Actions и GitLab CI в README.

**M7 — поставка.** Статический бинарник собирается в CI под linux-x86_64/aarch64 и macos-x86_64/arm64, публикуется в Releases с checksum и подписью, ставится `install.sh`, работает `self-update`; харнесс извлекается из бинарника и запускается под внешним `php.binary`. Опционально: скоупленный PHAR ставится через `composer require --dev` в проект, где уже есть другие версии `nikic/php-parser` и Rector, и работает без конфликтов (это интеграционный тест в CI). `opmin init` и `opmin doctor` работают, Docker-образ собирается в CI. Режим git-пакета работает в Docker с `--no-scripts` и без сети на этапе тестов.

## Целевая кодовая база

Тулза должна работать с любым из вариантов:

| Вход | Пример | Как работаем |
|---|---|---|
| Проект на фреймворке | `opmin optimize .` в корне Laravel/Symfony | Автолоадер, тесты и PHPStan проекта. Пути берутся из `opmin.yaml`, по умолчанию `src/` или `app/` (что найдётся) |
| Пакет из git | `opmin optimize git@github.com:vendor/pkg.git --ref=v2.1` | Клонируем во временный workspace, `composer install`, работаем там. Результат: ветка `opmin/<ts>` в клоне + `.patch` файл |
| Файлы / группы файлов / директории | `opmin optimize src/Foo.php lib/ 'src/**/*Service.php'` | Несколько путей и glob-ов в одной команде. Если рядом нет `composer.json` — работаем без автолоадера |

Следствия, которые надо учесть:

- **Корень проекта ищется автоматически** — вверх от переданных путей до `composer.json`. Нашёлся — подключаем его автолоадер, тесты, PHPStan. Не нашёлся — режим «голые файлы».
- **Режим «голые файлы»:** тестов нет, автолоадера нет. Проверка поведения только `php -l` + дифференциальное тестирование. Классы, которые зависят от отсутствующих классов, дифф-тестировать нельзя — такие функции получают статус `unverified` и по умолчанию **не меняются** (флаг `--allow-unverified` с явным предупреждением).
- **Не git-репозиторий:** вместо коммитов — копия исходников в `runs/<ts>/original/` и откат из неё. Результат — изменённые файлы на месте + `.patch`. Флаг `--dry-run` для всех режимов: ничего не трогать, только отчёт и патч.
- **Тесты проекта прогонять выборочно**, если возможно: по `@covers` / coverage-карте определить тесты, которые затрагивают изменённую функцию (`--filter`). Полный прогон — на финальной проверке. Иначе на большом проекте каждый шаг будет занимать минуты.
- Компилировать для подсчёта нужно **только целевые файлы**, а не весь проект, но в контексте автолоадера проекта — чтобы оптимизатор видел те же константы и классы.

## Изменение сигнатур и phpdoc

Решение: менять можно, если поведение не меняется или это доказуемо. Но у типов в PHP есть подвохи, поэтому правила такие.

**phpdoc** — менять свободно, рантайм не влияет. Задача — уточнять (`@param array` → `@param list<int>`), потому что это даёт PHPStan и дифф-тестеру больше информации. Ухудшать нельзя.

**Нативные типы — опасно, потому что меняют поведение даже когда «всё сходится»:**
- В режиме без `strict_types` добавление `int` к параметру включает **приведение**: `'5'` превращается в `5`, `'5.0'` и `true` тоже приводятся. Тип `strict_types` определяется **вызывающим** файлом, а не файлом функции.
- Значения, которые раньше проходили, начинают бросать `TypeError`.
- У переопределяемого метода изменение сигнатуры ломает наследников и реализации интерфейса (фатал по LSP), включая код вне проекта (у пакетов).
- Return type добавляет `VERIFY_RETURN_TYPE` (+1 опкод), если оптимизатор не смог доказать тип и убрать проверку. То есть типы могут как уменьшить счёт (оптимизатор выкидывает `is_int`-проверки и спецификует операции), так и увеличить. Только замерять.

Правила для нативных типов:
1. Менять можно только у функций, которые **нельзя переопределить снаружи**: `private`, `final`, методы `final`-классов, обычные функции. Публичные переопределяемые методы — только с флагом `--allow-public-signatures` (для приложений, не для пакетов).
2. Тип добавляется, только если PHPStan доказывает, что **все вызывающие** уже передают значение этого типа (без приведения). Если хоть один call site неизвестен (динамический вызов, callable-строка, рефлексия) — не трогаем.
3. Для пакета (режим git/пакет) по умолчанию публичное API не трогаем вообще — его вызывают снаружи, а call sites неизвестны.
4. Дифф-тестер для изменённой сигнатуры обязательно гоняет входы **за пределами** нового типа (строки-числа, `null`, `bool`, `float` для `int`) и сравнивает: старая версия и новая должны вести себя одинаково, включая `TypeError`. Если старая принимала `'5'`, а новая бросает — изменение отклонено.
5. Удаление/расширение типа — тоже изменение поведения (пропадает `TypeError`), правила те же.

Конфиг:

```yaml
signatures:
  phpdoc: true                     # уточнять phpdoc
  native_types: non_overridable    # none | non_overridable | all
  public_api: false                # трогать публичные переопределяемые методы
```

Для режима пакета `public_api` принудительно `false`, если не передан `--force-public-api`.
